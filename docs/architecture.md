# Architecture: 24goods

**Status:** v0.2 (MVP-0 implemented). Rationale and trade-offs for every change since v0.1 are in [review-v2.md](review-v2.md); the original platform evaluation is in [analysis.md](analysis.md).

**Priorities:**
1. Security
2. Correctness of money and stock
3. Speed from mainland China
4. Developer velocity

**Rules:**
- Only `web` publishes a port. Docker-published ports bypass UFW, so nothing else may ever get `ports:`.
- Each container receives **only its own** env file (`deploy/env/<service>.env`, generated by `deploy/bootstrap.sh`).

## 2. Production server allocation (M1)

Unchanged in intent from v0.1:

| Host | Role |
|---|---|
| SoftBank JP | Edge / CN entry: Caddy + CrowdSec; holds no data and no keys |

**Starting point:** one domain, standard automatic HTTPS. A second CN entry hostname is added **only if** measured CN latency justifies it.

**Latency rule:** if p99 RTT × DB round-trips exceeds 30% of the 150 ms server-side p95 budget, consider colocating the API with PostgreSQL. This is a manual decision recorded as an ADR, never automatic ([review-v2 §6.3](review-v2.md#63-latency-decision-rule-replaces-5-ms)).

## 3. Components

| Component | Implementation |
|---|---|
| API | FastAPI modular monolith: `auth`, `catalog`, `chat` (+quotes), `orders`, `payments` (notify), `inventory`, `uploads`, `realtime`, `admin`. SQLAlchemy 2 async + asyncpg, Alembic. One process serves the public app (:8000) and an internal app (:8081). |
| Delivery service | Separate process. Outbox consumer (`FOR UPDATE SKIP LOCKED`) plus a Starlette-only internal reveal API. The only holder of private keys. FastAPI/pydantic are not loaded (enforced by test). |
| Jobs | Durable work goes through the PostgreSQL **outbox** (same transaction as the state change). Order expiry runs as an asyncio task in the API. |
| Realtime | **SSE** over Redis pub/sub (`rt:*` channels), with a 15 s heartbeat; clients fall back to polling. Centrifugo is deferred until there is more than one API node or more than ~2k concurrent connections. |
| Frontend | Two static Vite SPAs in one pnpm workspace (`web`: Vant 4, `admin`: Element Plus, `shared`), served by Caddy. **No Node at runtime.** Web initial JS is 77 KB gzip (budget 150 KB). |
| Payments | `PaymentAdapter`-style ZPay adapter on the EPay protocol (`app/payments/epay.py`, `zpay.py`). USDT (BEpusdt) is phase 2. |
| Uploads | Local volume in the demo; a private R2 bucket proxied via the edge in production. Served only through `/api/v1/files/{id}` with authorization. |
| Search | PostgreSQL full-text search + `pg_trgm` |

## 4. Data model (implemented, `migrations/versions/0001_initial.py`)

Every tenant table has `tenant_id`, with **ENABLE + FORCE ROW LEVEL SECURITY** and the policy `tenant_id = current_setting('app.tenant_id')::uuid`. An `after_begin` hook pins the tenant on every transaction, and background jobs pin the tenant per job.

Tables:
- `tenants`, `users`, `agent_status`, `custom_domains`
- `products` (i18n jsonb, `price_minor`, `floor_price_minor`, `delivery_mode`)
- `card_stock` (`blob` bytea, `fingerprint`, `kid`, `status`, `order_id`)
- `conversations`, `messages` (bigserial ids, `UNIQUE(sender_id, client_msg_id)`), `attachments`
- `quotes` (HMAC-signed, versioned)
- `orders` (random `order_no`, `version`, `quote_id UNIQUE`), `order_events`
- `payments` (`UNIQUE(channel, gateway_trade_no)`, `UNIQUE(order_id)`)
- `deliveries`
- `ledger_entries` (append-only by grants; a deferred trigger enforces Σ = 0 per transaction)
- `outbox`, `audit_log`

Money is stored as `bigint` minor units plus `currency`. Floats are never used.

**Roles** (non-superusers; the superuser exists only for initdb):

| Role | Privileges |
|---|---|
| `app_owner` | Owns the schema; `CREATEROLE`; runs migrate and seed; bound by FORCE RLS |
| `app_api` | `INSERT` on `card_stock`, but **no `SELECT` on `blob`** (column grant); normal CRUD elsewhere |
| `app_delivery` | Reads `blob`; updates only `status`/`order_id`; writes deliveries, events, messages, ledger, audit |

## 5. Card-key vault and key lifecycle

- **Crypto** (`app/core/cardvault.py`): one DEK per card, AES-256-GCM. The DEK is wrapped with X25519 ECDH + HKDF-SHA256 + AES-GCM. AAD = (tenant, product, card_id), so a row swap fails to decrypt. A keyed, tenant-scoped HMAC fingerprint provides dedup.
- **Isolation, four layers:**

| Layer | API | Delivery |
|---|---|---|
| Process | `CardSealer` with public keys only; refuses to start if a private-key file is configured | `CardOpener`, the only process with private keys |
| Secret | `vault_public_keys` | `vault_private_keys`, mode 0400, owned by the container uid |
| Database | No `SELECT` on `blob` | Reads `blob` |
| Network | edge + backend | backend only, with **no egress** |

- **Reveal:**
  1. The buyer calls `POST /orders/{id}/reveal`.
  2. The API checks the session and owner, then calls `delivery:8001/internal/reveal` with an internal token (constant-time compare).
  3. Delivery re-checks the owner and the delivered state.
  4. It applies a per-order limit (10/h), a per-buyer limit, and a **global circuit breaker** (30 decrypts/min → 503 + CRITICAL log). A request larger than the remaining budget is rejected before counting.
  5. It writes an audit row and returns the codes with `Cache-Control: no-store`.
- **Lifecycle:** generate with `app.devtools.keygen` (offline in production) → distribute (public key to the API, private key to delivery only) → keep in memory only → back up with age to two offline copies (never in DB backups) → rotate (new `kid` + `rewrap()`) → on **compromise**, revoke, void unsold stock under that `kid`, re-import, notify buyers → destroy. Details: [review-v2 §4](review-v2.md#4-key-isolation-concrete-design).
- **Card import:** `POST /admin/products/{id}/cards/import` is **admin role only**, ≤5000 lines, rate-limited, audited, sealed immediately; plaintext is never echoed. Production adds TOTP step-up and an admin-only network path (M1) and two-person approval for bulk imports (M2).

## 6. Payment pipeline: ZPay Alipay v1

```
pay:    server-priced order ─► signed submit.php URL (no key in URL) ─► buyer pays
notify: GET /api/v1/pay/notify/zpay   (per-IP rate limit; bad-signature audits sampled)
  1 pinned-MD5 signature (constant time) · pid · out_trade_no · TRADE_SUCCESS · exact Decimal amount
  2 Redis replay guard: 60 s IN-FLIGHT lock → promoted to 24 h "done" only after settling
    (a crash mid-settle never blocks ZPay's retries for long)
  3 re-query api.php?act=order (≤3 s total; ZPay waits 5 s): paid, same money, same trade_no, same out_trade_no
  4 BEGIN · order FOR UPDATE · already paid → success · pending → paid
    · late (expired/cancelled, however late) → manual_review, still recorded
    · amount changed after pay URL → manual_review
    · INSERT payments (UNIQUE) · ledger Σ=0 (+ 1.6 % fee txn) · outbox(order.paid) · COMMIT
  5 "success" (also for manual_review, audited) / "fail" (bad sig, outage → ZPay retries)
return_url → display only (redirect to the order page)
```

Prod guards: the gateway and the query base must be `https://`, `APP_COOKIE_SECURE=true`, and the mock gateway refuses to run outside `dev`/`test`. M1 adds a reconciliation job that polls the query API for `pending_payment` orders with a pay attempt, plus external alerting on `manual_review`.

## 7. Chat and negotiation

```
Product "Chat"  → POST /conversations {product_id} → find-or-create + product_card snapshot
Agent "Quote"   → POST /admin/conversations/{id}/quotes → quote (HMAC, expiry, qty≤10 for auto_card) → quote_card
Buyer "Accept"  → POST /quotes/{id}/accept → TX: lock quote, verify → order(pending_payment, quote amount)
Agent "Price"   → PATCH /admin/orders/{id}/price (pending only, ≥ floor×qty, version++, audited, system msg)
Buyer "Pay"     → POST /orders/{id}/pay → ZPay → §6 → delivered (auto) | agent delivers (manual) → confirm
```

- **Message types:** text, image, voice (≤60 s, ≤1 MB, webm/ogg/mp4), product_card, quote_card, order_card, system. When a card's state changes, the server re-publishes the message under the same id, so the client replaces it.
- **Agent status:** online / away / on_hold / offline. Buyers see the best status across agents.
- **Staff Inbox:** filters (all / mine / unassigned), assign, unread counts, close, quote composer, and the buyer's recent orders.
- **Not built:** voice **calls**, which were dropped ([review-v2 §0](review-v2.md#0-what-changed-summary)).

## 8. Security controls

| Threat | Controls (✅ in MVP-0, ⏳ planned) |
|---|---|
| Card-key theft | §5 ✅ |
| Forged or replayed callbacks | §6 ✅; tests cover forged/tampered/wrong pid/downgrade/replay/concurrency/crash-mid-settle/timeout/late |
| Price tampering | Server prices; HMAC quotes; versioned, audited price changes ✅ |
| Cross-tenant access / IDOR | FORCE RLS + per-transaction pinning; owner checks with a uniform 404; cross-tenant tests ✅ |
| Session attacks | Hashed session keys in Redis, rotation on login, HttpOnly, SameSite=Lax, `__Host-` prefix over HTTPS, CSRF header ✅ |
| Brute force / CC | Redis limits: failed logins per (email, ip) + per email; register; messages; uploads; orders, pay and accept per user; ≤5 pending orders per buyer; notify per IP ✅. Edge: Cloudflare / CrowdSec ⏳ M1 |
| Malicious uploads | Magic bytes, single-format decoder, pixel caps, re-encode, EXIF stripped, random keys, `CSP: sandbox`, `nosniff`, voice served as attachment ✅. Separate media origin ⏳ M1 |
| Secret sprawl | Per-service env files, Redis ACL users, column grants, a private-key file only in delivery ✅ |
| Supply chain | SHA-pinned Actions, Dependabot with a 7-day cooldown, pip-audit / pnpm audit, Trivy, gitleaks ✅ |
| On-demand TLS abuse | `ask` endpoint: internal listener, verified domains only, normalization, negative cache, rate limit ✅ (block disabled until M4) |
| Independent audit | ⏳ **M1 exit gate**: no real money before it |

### ADR-015: List storefront, generated covers, Kesiv brand config
- **Context:** The reference shops (gmailbuy and others) sell by plain, dense lists with tags in the title; buyers of virtual goods compare price and stock, not photos. Most products have no image.
- **Decision:** The default product view is a grouped list (56 px thumbs, price, stock, Buy) with an optional grid toggle. A missing cover is a deterministic SVG generated client-side from the title and category. Every brand string lives in `packages/shared/src/brand.ts` (+ `APP_BRAND_NAME` for meta).
- **Consequences:** No image storage or generation endpoint is needed; a rename is a one-line change. Covers can't be customised server-side until a real image is uploaded.

### ADR-016: Instant accounts + self-hosted PoW instead of guest checkout
- **Context:** Guest checkout would leave chat, after-sales, reveal budgets and order history without an identity, and anonymous orders can't be rate-limited per buyer.
- **Decision:** One-tap instant account (`POST /auth/instant`): random handle and password returned once, a normal buyer row with `is_instant=true`. Abuse is limited by a self-hosted HMAC-signed, single-use proof-of-work (no third-party captcha because of China reachability and privacy), per-IP limits (3/h, 10/day), a hard per-/24 (/48) cap of 200/day with a soft ramp (+4 / +6 PoW bits above 30 / 100 accounts per net today), at most 2 pending orders, and a 7-day purge of unpaid instant accounts. Instant accounts are created without an email; an email can be added later and is unverified until email verification (M1).
- **Consequences:** Everything downstream keeps one identity model. CGNAT or office networks are slowed down, not blocked. Email ownership is unverified, so the credentials path uses a generic conflict message and the gap is a tracked known issue.

### ADR-017: Access-code order lookup
- **Context:** Lookup by order number alone is an IDOR (guessable numbers); buyers who lose instant credentials still need their codes.
- **Decision:** Every order gets a 10-char Crockford base32 access code (50 bits), stored only as `HMAC-SHA256(lookup_key, order_no || code)`. `POST /lookup` and `/lookup/reveal` need order no + code and never create a session. Order of checks: per-IP limit, verify the code, and only on failure count it per `order_no:ip` (5/h) and per order (50/h). A correct code is never blocked by the per-order counters, so nobody can lock a buyer out.
- **Consequences:** Reveal goes through the same delivery service and budgets as the signed-in path. At 50 failures/h per order, guessing 2^50 codes is infeasible. `APP_LOOKUP_KEY` is mandatory in prod; rotating it invalidates all existing codes (buyers can rotate individually).

### ADR-018: Card management without plaintext
- **Context:** Staff need to find, void and replace cards, import batches and expire them, but invariant 1 forbids plaintext outside the vault and the delivery worker.
- **Decision:** Cards carry a keyed fingerprint (content) and a `lookup_fp` (first field, case-folded), both HMACs with the vault fingerprint key. "Find" recomputes the fingerprint of what the admin pastes and matches; it never decrypts and returns masked values only. Void/replace are state changes with a reason (`defective`, `expired`, ...); batches record imports; `expires_at` drives an hourly void job. `/admin/cards/find` is audited with counts only and limited to 30/h per admin.
- **Consequences:** Find is an existence oracle for people who already hold a code, so it is admin-only, rate-limited and audited. Replacement claims fresh stock in the delivery worker and records the acting staff member.

### ADR-019: After-sales, auto-confirm and recorded refunds
- **Context:** Digital goods need a warranty window and a way to settle disputes; unconfirmed orders must not hang forever, and money movement must not be silent.
- **Decision:** `after_sales_until` and `auto_confirm_at` are snapshotted at delivery (site default 28 d / 72 h manual, 24 h auto_card; per-product override). A buyer opens one ticket per order; staff can process, replace (manual: new text; auto_card: outbox job in the delivery worker), reject, resolve; refund is admin-only and, from the 3rd replacement, replace needs an admin. Opening a ticket bumps `order.version` and pauses auto-confirm; the job re-checks for open tickets under the order lock. A refund only RECORDS the refund (order `refunded`, balanced reversal ledger entries, audit); the money goes back through the Alipay console until a refund API is integrated. Late payment notifies for a refunded order with the same trade number are acknowledged without effect.
- **Consequences:** The ledger and the gateway can diverge if staff forget the console step; reconciliation (M1) must flag it. A refunded order's cards are never revealable (409).

### ADR-020: Production edge: Cloudflare proxied + Origin CA + Authenticated Origin Pulls on port 8088
- **Context:** `shop.kesiv.com` is served from one non-mainland host behind LXD NAT. We want public TLS, DDoS absorption and a hidden origin without running ACME on the host, and the staff console must not be reachable by the whole internet.
- **Decision:** DNS is Cloudflare-proxied (SSL Full strict); an Origin Rule sends traffic to origin port 8088. Caddy there serves HTTPS with a Cloudflare Origin CA certificate and requires a client certificate (`client_auth require_and_verify`, Authenticated Origin Pulls), so a direct hit on the origin IP fails the TLS handshake. Caddy trusts `CF-Connecting-IP` only from the hard-coded Cloudflare ranges (`trusted_proxies_strict`) and passes `X-Forwarded-For: {client_ip}` to the API, which trusts only the Caddy container (10.89.10.10). `/admin`, `/admin/*` and `/api/v1/admin/*` are answered 403 unless the client IP is in `ADMIN_ALLOW_IPS`. A loopback-only `:80` site exists only for the container healthcheck. Dev and prod run the same images and base compose; prod adds an override file and a Caddyfile.
- **Consequences:** The Cloudflare IP list is static and must be refreshed (rarely changes; if stale, visitors from new ranges would be seen as Cloudflare IPs, which fails closed for the admin allowlist). Cloudflare idles out requests after 100 s; the SSE heartbeat is 15 s. The allowlist is IP-based: staff outside it need a change in `.env` plus `compose up -d web`; a VPN or Cloudflare Access is the better long-term answer. Cloudflare sees all traffic in clear text (accepted).

### ADR-021: Checkout-level payments and a buyer-paid channel surcharge
- **Context:** ZPay charges the merchant 1.6 %, and the owner wants buyers to carry a channel fee (default 3 % for Alipay) so every sale is profitable. A cart should be payable in one go, but a gateway trade maps to one `out_trade_no`, and one card-key order must still be fulfilled independently of its siblings.
- **Decision:**
  - *Surcharge.* The fee is computed server-side at order creation: `fee = ceil(subtotal * permille / 1000)` (integer maths), `amount = subtotal + fee` (DB CHECK), the rate is stored on the order (`fee_permille`) and configured in `tenants.settings.payments.channels` (default 30 permille, range 0-200). Paying with a channel whose rate differs from the stored one re-applies that channel's fee while the order/checkout is unpaid (issue 23, supersedes the original `fee_channel_mismatch` refusal): fee/amount/version are rewritten under the row lock and audited; the old pay URL / USDT attempt is not honoured because its notify amount no longer equals `amount_minor` and goes to manual review; once a `payments` row exists the switch is refused (`invalid_state`). Views expose server-computed `channel_totals` per enabled channel and the cart preview uses the same per-line ceiling. Admin price changes set the new subtotal and recompute the fee. The ledger splits a payment into `gateway_clearing +amount`, `sales_revenue -subtotal`, `surcharge_revenue -fee`; refunds mirror the lines; the 1.6 % gateway cost entry is unchanged.
  - *Checkout.* A cart creates one order per line (own order_no, access code, fee, fulfilment) plus a `checkouts` row (`C` + 12 base32) whose `amount_minor` is the sum. The gateway sees only the checkout (`out_trade_no = checkout_no`); member orders refuse to be paid directly (`pay_via_checkout`). The notify keeps the full pipeline of ADR-007 (signature, pid, exact amount against the checkout, status, re-query, replay guard) and then settles under locks taken in a fixed order (checkout `FOR UPDATE`, then orders `ORDER BY id FOR UPDATE`), with one `Payment(checkout_id)` (`UNIQUE(checkout_id)`, `UNIQUE(channel, trade_no)`). The per-order paid transition (status, events, ledger, outbox `order.paid`, `sold += qty`, chat and buyer-input messages, audit) is ONE helper (`payments/settle.py::settle_member`) shared by the single-order and checkout paths, so both behave identically. A checkout that is expired or cancelled makes every member late (manual review, money recorded, nothing fulfilled).
  - *Cancel.* Buyer and staff cancel are one code path: only `pending_payment`, a member order cancels the whole checkout, and if a pay URL was ever issued the gateway is queried first without holding locks (paid -> settle normally and answer `already_paid`; query failure -> 503), following Alipay's "query before close".
  - *Open orders cap* counts payables (pending single orders + pending checkouts), not member orders.
- **Consequences:** Buyers see one extra transparent fee line; sales stay at list price. A checkout cannot be partly cancelled or re-priced (staff close it instead). A tenant that changes the rate invalidates pending orders created at the old rate for payment (they expire or are recreated). Legacy orders have fee 0 and keep working. Fulfilment, refund and chargeback stay per order, so a refund of one member reverses only its lines. Payment lookups for an order use `order_id OR checkout_id`.

### ADR-022: Cloudflare Turnstile script is a documented exception to "no third-party runtime assets"
- **Context:** Owner wants a Turnstile shield on login/register/instant/reset/lookup. Cloudflare forbids self-hosting `api.js`; invariant 8 forbids runtime third-party/CDN assets.
- **Decision:** the frontend loads `https://challenges.cloudflare.com/turnstile/v0/api.js?render=explicit` only when `GET /site` reports `turnstile.enabled` and only on a protected form. Verification is server-side (`app/core/turnstile.py`): tokens are single use (Redis 5 min), siteverify has a 5 s timeout and fails closed; enabled-without-secret is treated as disabled so a misconfiguration cannot lock out staff. Off by default. The secret lives AES-256-GCM sealed in `tenant_secrets` (`app/core/secretbox.py`, key `APP_SETTINGS_KEY`, AAD `tenant_id|name`).
- **Consequences:** Cloudflare sees visitors of protected forms (reachable from mainland China in practice, but a block degrades to the fallback of leaving Turnstile off). CSP must allow `challenges.cloudflare.com` for script/frame/connect only on those pages. Audit retention purge goes through a bounded SECURITY DEFINER function (`purge_audit_log`, rows older than 30 days only) so `app_api` keeps no table-level DELETE on `audit_log`.

### ADR-023: USDT via self-hosted BEpusdt as three fixed channels (MVP, no provider-instance model)
- **Context:** The owner wants to receive USDT (docs/review-v5.2.md §7, research in `docs/research/bepusdt.md`). A generic "provider instances" model (v5.1 §4) is more than the MVP needs.
- **Decision:**
  - *Channels.* `usdt_arbitrum`, `usdt_xlayer`, `usdt_trc20` sit next to `zpay_alipay` in `modules/payments/channels.py` with the same `enabled` / `surcharge_permille` tenant config, **disabled by default** (surcharge default 0). Entry pricing of an order uses the first enabled channel and is re-applied at pay time as before. `settle.py` takes the channel as a parameter: `payments.channel`, `orders.channel`, ledger account `gateway_clearing:{zpay|bepusdt}` and memo `{provider} payment ...` follow it; BEpusdt has no gateway-cost entry. Refunds mirror the lines of the order's own channel.
  - *Gateway.* BEpusdt (`v03413/bepusdt:v1.24.3`) runs on its own docker network (`usdt`, shared with `api` only), with no published port and no Caddy route; its console is reached through an SSH tunnel. Adapter `payments/bepusdt.py` (config `APP_BEPUSDT_URL`, `APP_BEPUSDT_API_TOKEN` in `api.env` only). The order amount stays CNY: `create-transaction` is called in fixed-amount mode (`amount > 0`, `fiat=CNY`, `order_id = order_no | checkout_no`). Signature: upstream's MD5 scheme, pinned, compared with `hmac.compare_digest`; a notify is also accepted when the JSON floats are rendered without trailing zeros (how a Go float64 is stringified), both variants being keyed with the token.
  - *Notify.* `POST /pay/notify/bepusdt` (JSON, exempt from CSRF and the global limiter): signature -> `order_id` is an order/checkout of THIS tenant -> `status` (1 waiting / 3 expired: reply `ok`, no state change, no audit per ping) -> `amount` exact `Decimal` == order amount (else manual review) -> the order was opened on a USDT channel -> Redis replay guard -> server-to-server `POST /api/v1/pay/info {trade_id}` must say status 2, same `order_id`, same `money`, `fiat=CNY` and a `trade_type` that maps to the order's channel -> the existing settle pipeline (row lock, state machine, `UNIQUE(channel, gateway_trade_no = trade_id)`, ledger, outbox). **Known defect, #26 (2026-11-08):** the pinned upstream native POST notifier accepts any HTTP 200 and ignores its body. Current `200 fail` replies therefore suppress retries. Intended behavior is HTTP 200 only for durably accepted/idempotent or harmless outcomes, and non-200 for retryable failure; the code fix is pending. See the [pinned-source evidence](research/security-payment-audit-2026-11-08.md#f0--bepusdt-http-200-failure-replies-permanently-acknowledge-failed-callbacks). `actual_amount`, `token` (address) and `block_transaction_id` are kept in `payments.raw` (audit); the crypto amount is never trusted for money. Cancel re-queries the stored `trade_id` first (currently Redis-dependent; durable attempt storage is pending).
  - *Buyer UI.* The pay endpoint returns our own page `/pay/usdt/{no}`; `GET /api/v1/pay/usdt/{no}` (owner only) serves network, address, exact USDT amount, countdown, order status and a server-generated QR (segno, pure Python, SVG, rendered via an `<img>` data URI). The page polls the status; the BEpusdt checkout page is never exposed.
  - *Attempt state.* The BEpusdt attempt (trade_id, address, `actual_amount`, expiry) is kept in Redis (`usdt:attempt:{no}`, 7 d TTL), not a new table: it is display state and the cancel re-query key, while fulfilment re-derives everything from the gateway re-query and the order. An unexpired attempt for the same channel and amount is reused; otherwise BEpusdt rebuilds the trade for the same `order_id`.
- **Consequences:** MD5 stays weak but is bounded by the re-query over the internal network. If Redis loses an attempt the pay page 404s until the buyer presses pay again (a fresh trade is created); a payment to an old trade still settles through the notify (or lands in manual review if it was cancelled/expired). Cancelling an order does not cancel the BEpusdt trade (a later payment becomes a late payment in manual review). Switching channel after a pay URL was issued is refused when the fee rate differs (`fee_channel_mismatch`, ADR-021). Adding a fourth network is a one-line change in `USDT_CHANNELS`. Network: `api` and `bepusdt` share the `usdt` network so the notify can reach `api:8000`; bepusdt can then also reach the api's internal listener (:8081, read-only rate-limited TLS ask) — accepted (security review 2026-11-07). The image is pinned by digest (Docker Hub has no semver tags: v1.24.3 = `0716485`).

### ADR-027: Record legacy pay URLs; the record adds checks, never removes them

Context: the environment-key EPay path signed a `submit.php` URL and recorded nothing, so every later decision about whether money could still arrive through it — chiefly whether a cancel is safe — was inferred from the current channel, key presence, cutover time or provider history. All four can change after the URL is issued. An independent payment audit (2026-11-08) showed the inference failing both ways: cancels proceeding over a live legacy URL after a channel switch, a provider cutover or full de-configuration (fail-open), and every EPay cancel returning 503 for a tenant on durable providers with no env key (fail-closed false positive).

Decision: write a `legacy_pay_urls(tenant_id, local_ref)` row in the transaction that commits before the URL is returned; it is RLS-enforced and append-only for `app_api`. A migration backfill marks every payable pending at deploy time. On cancel, a recorded URL is always queried, whatever the channel or provider history, and fails closed (503) when the signing key is gone. With no record and no key, the cancel proceeds. With no record and a key present, the earlier best-effort query (v4 review W2/W3) is kept. The record adds certainty but never removes a check. In the same pass, reconciliation carries committed outcomes through any exception type, collects them in a caller-owned sink so a `wait_for` timeout cannot lose them, marks an attempt settled inside the settlement's own commit, and alerts on every distinct duplicate trade.

Consequences: the backfill over-marks (USDT and durable-provider payables included), so on a deployment with no env key a payable pending at deploy time cannot be cancelled manually; it returns 503. This is bounded: every order and checkout gets an `expires_at` from the tenant TTL at creation, and the expiry job does not pass through the cancel gate, so these expire on schedule. Only rows that predate expiry altogether could be held longer. The cost is deliberate: under-marking would allow cancels over money. The pay flow re-checks that the payable is still pending after the marker commits, so a cancel that completes inside the pay window never leaves a URL in the buyer's hands. Late legacy notifies for a payable that also has a durable attempt are still rejected into manual review, so a paid legacy URL is caught by cancel or by staff, never silently dropped. Unexpected reconciliation errors now become 503 (logged with traceback) rather than 500, and one failing ref no longer aborts the tick for the remaining tenants.

### ADR-031: order, stock, refund and subscription integrity (review-v8, issue #59)

Context: the last auto-card could be sold twice (stock was only checked, not reserved, so the second paid order landed in `manual_review` with no way out); "refunded" only recorded a ledger entry, not that the money went back; a refunded subscription renewal left the full service period in place; the reseller balance ignored open disputes; manual stock release returned `qty` even when the stock had been unlimited at order time; and an order's after-sales/subscription terms followed later product edits.

Decision: (A) auto-card stock is reserved by count: creation takes the product row lock (after the buyer row, before the promo row) and requires `available - reserved >= qty`, with `reserved` derived from orders in `pending_payment`/`paid`, so expiry and cancellation release it without extra state. Held orders get an admin-only `requeue-delivery` that re-verifies a succeeded payment covering the order, an open ledger posting and stock, then re-emits `order.paid` under a per-requeue outbox key. Paid-undelivered goods orders can be refunded by an admin through the same routine as after-sales, and buyers can escalate `not_received` once the delivery ETA (1 h for auto-card) has passed. (B) Every refund requires a 3-200 character `reference` (staff confirm the money was already returned); it is stored in the `refunded` order event, the audit detail and shown to the buyer. No new states: a two-phase refund with provider APIs belongs to #55. (C) `sync_subscriptions` reverses refunded renewals period by period (`service_renewals.reversed_at`) and a refunded source order only cancels the service when no paid renewal remains (otherwise `source_reversed_at` and one period is taken back); an ambiguous subtraction (would end before the start) is left untouched and recorded once as an operation event. (D) `reseller.balances` holds back markup of orders with an `open`/`processing` ticket (`disputed_minor`). (F) `orders.terms` snapshots after-sales hours/months and the subscription config at purchase; legacy rows (NULL) fall back to the product. (G) `orders.stock_reserved` records what was actually reserved; release gives back exactly that and zeroes it.

Consequences: a refund of a `manual_review` order only reverses the ledger when a payment posting exists (payment anomalies may have none). Reservation counts paid-but-undelivered auto-card orders until the worker consumes the cards, so a stalled worker temporarily shrinks sellable stock rather than overselling. Migration `0015_order_integrity` is additive; the delivery worker only reads `orders.terms` under its existing table-level SELECT, and app_api gains UPDATE on `service_renewals`.

### ADR-033: payment-channel resilience and diagnostics (review-v9, issue #63)

Context: on 2026-11-09 the EPay host stopped accepting TCP connections from production. `prepare()` marked the attempt `unknown`, so every later pay and cancel for the checkout returned 503 until it expired, and the reconciler re-queried every 2 minutes. "Unknown" is right when a request may have reached the gateway, but a connect failure proves it did not.

Decision: transport errors are classified in `app/payments/zpay.py` (`ZPayUnreachable`, a `ZPayQueryError` subclass, for DNS failure, `ConnectError`, `ConnectTimeout`; the connect timeout is shorter than the overall one so a dead host is told apart from a slow one). The prepare path marks such an attempt `failed` (`data.reason = gateway_unreachable`, audit `payment.attempt_failed`) and answers 503 `channel_unreachable`; read timeouts and protocol errors keep `unknown`. `requery_all` skips `failed` attempts (never dispatched, or released by staff). An admin may release an `unknown`/`preparing` attempt (`resolve`, outcome `not_paid`, note 10-500 chars, audit warning + operation event); a payment that still arrives takes the normal late-payment path (manual review), so no invariant in section 1.2 is relaxed. The reconciler re-queries unknown attempts every 2 minutes for the first hour and hourly after that, and after 24 h raises one critical operation event plus a Telegram notice and stops polling. Channel self-test (`/test`) connects from the server and sends a signed query for a random non-existent order, reporting the gateway's message with the key redacted; health is derived from the last test and the last 30 minutes of attempts (a newer successful test outweighs older failures). Checkout member orders carry `channel` as soon as the checkout's channel is set. Migration `0017_payments_v9` backfills pending checkouts and adds `users.announcement_ack` (highest acknowledged announcement version, so a mandatory acknowledgement follows the signed-in buyer). Manual delivery: the paid notice for a manual goods order is one urgent desk alert and Telegram message; the buyer's "Remind seller to ship" (`POST /orders/{ref}/expedite`) writes an `order_events` row with reason `expedite` (cooldown 30 min, max 3, the count lives in those rows) and a system message into the order conversation. The visit gate covers every storefront route; only a 428 raised mid-session degrades to the docked banner.

Declined: a random Alipay amount tail. EPay orders carry our own `out_trade_no` and signed notifies, and adding offsets to evade a provider's risk controls would endanger the merchant account.

Consequences: a buyer whose gateway is down can switch method or cancel at once; staff keep an audited way out of a genuinely stuck attempt. Releasing an attempt is a staff judgement call that is recorded; money arriving afterwards is still caught by the notify and reconciliation path. The self-test never creates a charge.

Audit follow-ups (same ADR): a `failed` attempt is a conclusion drawn without gateway evidence, so it is never final for money. (1) A notify never consults attempt status: for a failed or released attempt it is verified and re-queried like any other, so a pending order becomes `paid` and a cancelled/expired one goes to `manual_review` (tested). (2) The reconciler re-queries `failed` attempts with reason `gateway_unreachable` or `resolved_not_paid` younger than 24 h at most every 10 minutes and settles through the same path (`recheck_failed`). (3) Releasing a `preparing` attempt needs it to be older than 2 minutes, and `prepare()` re-reads the attempt under its row lock before recording the gateway result: if staff released it meanwhile the result is dropped, the pay URL is not handed out and the buyer gets `channel_unreachable`. (4) The member-channel backfill lifts FORCE RLS for its one statement and restores it in `finally` (the owner role has no tenant GUC); a test runs it without one. (5) The 3-per-order reminder cap answers 409 `expedite_limit`.


### ADR-034: several EPay gateways, priority + sticky failover, test payments (review-v10)

Context: the owner adds more than one EPay-compatible gateway and wants the one that worked last time reused, a visible/settable priority, and a way to verify a channel by paying through it. Until now a tenant had a single active gateway (`payments.epay_provider_id`).

Decision: `payment_gateways` gains `priority` (lower first), `enabled`, `last_ok_at`, `last_fail_at`, `last_fail_reason` (migration `0018_gateway_routing`; backfill keeps the currently active gateway enabled at priority 10 and disables the rest; new gateways are created disabled until the admin enables them). Tenant setting `payments.epay_routing` is `sticky` (default) or `priority`. `gateways.candidates()`/`order_candidates()` order the enabled gateways: in `sticky` mode the gateway with the latest success goes first unless it failed since or an admin made another gateway primary after that success (`epay_primary_at`, written by the legacy `activate`, which now enables the gateway and gives it the top priority); the rest follow by priority. `prepare()` tries the candidates in order inside one pay request. Only outcomes that provably created nothing at the gateway fail over: `ZPayUnreachable` (connect level) and `ZPayRefused` (`mapi.php` answered well-formed JSON with `code != 1`; message truncated to 200 chars, key redacted). Each failed try ends its own attempt `failed` (`gateway_unreachable` / `gateway_refused`), updates the gateway's `last_fail_*`, audits and records an operation event, and the next candidate gets a fresh attempt (new out_trade_no, own `provider_id`). Anything ambiguous (read timeout, protocol error, non-JSON, HTTP 5xx) stops with an `unknown` attempt as before. All candidates failing is 503 `channel_unreachable`. A ready attempt is reused only when its gateway is still the first choice. Re-query, notify, reconcile, cancel and resolve keep using the attempt's own `provider_id`, so disabling or demoting a gateway never strands its in-flight payments. A paid, or successfully prepared, payment sets `last_ok_at`.

Admin API (session admin only, audited, tenant-scoped, rate limited): `GET /admin/payment-gateways` (adds `routing_mode`, computed `candidates`, per-item `enabled/priority/in_use/last_*`), `PATCH /{id}` (enabled, priority), `PUT /order` (ids = every gateway once, priorities 10, 20, ...), `PUT /routing` ({mode}), `DELETE /{id}` (409 once any attempt used it: disable instead).

Test payments: `POST /admin/payment-gateways/{id}/test-payment` (0.01-10.00 CNY, 10/hour/admin) creates a real payment through the normal `create_payment` with an out_trade_no in the reserved `T` + 16 hex namespace (orders are `G`, checkouts `C`), stored in `payment_tests` (RLS, never linked to an order). The response carries a server-rendered SVG QR (same renderer as the USDT page; no client QR library, no CDN). `GET /admin/payment-gateways/test-payments[/{id}]` lists/polls; a poll re-queries the gateway at most every 3 s. A notify for a `T` reference takes `handle_test_notify`: signature with that gateway's key, merchant id, exact amount, server re-query, row lock, idempotent flip to `paid`; it can never reach order settlement. A paid test books `gateway_clearing:zpay` +amount against a dedicated `test_receipts` account (balanced, `order_id` NULL), so clearing still reconciles and sales are untouched; the money is real and is refunded in the gateway console.

Consequences: a dead or refusing gateway costs the buyer at most its connect timeout before the next one is tried, and the order stays payable. Failover can leave a `failed` attempt per gateway tried (audited). With two enabled gateways a buyer may hold a QR from the first-choice gateway that later changes; the superseded attempt is still re-queried and settled by the existing multi-original recovery. PAYMENT notify and pay-page paths are unchanged apart from the `T` dispatch.

### ADR-035: Every held order and payment attempt has an exit (issue #72 B1-B3, S12, A1, A3, A4)

Context: an end-to-end audit (#72) found dead ends on the money path: a USDT refusal locked the order (no pay, no cancel); a `manual_review` order with no recorded payment, or a held manual-delivery order with a valid payment, had no staff action except a manual refund; payment attempts for abandoned orders were re-queried hourly for ever; a second paid trade on a refunded order raised no alert; a redirect-mode gateway was marked healthy without ever being contacted; a dead delivery job notified nobody; and two API replicas could run the periodic jobs at once.

Decision:
- **USDT refusal** (`BepusdtRefused`) ends the attempt `failed` (`gateway_refused`); only transport errors and timeouts stay `unknown`. The USDT re-query skips `failed`/`closed` attempts, so "resolve: not paid" unblocks cancel as well as pay.
- **Release hold** (`POST /admin/orders/{id}/release-hold`, admin, reason required, audited `order.hold_released`): `accept` needs the same verified-payment evidence as requeue (succeeded payment covering the amount, same currency, open ledger); auto-card is requeued, other orders become `paid` (manual stock re-reserved under the product lock, refused when none is left; `sold` counted when the hold came from the gateway). `close` needs NO payment for the payable and a fresh re-query of every attempt (the cancel path's `_settle_if_paid`) saying unpaid; an unresolved query fails closed (503), a paid answer is settled and the close refused (409 `already_paid`); a checkout closes as a whole. The order detail exposes `hold {reason, by, has_payment}`.
- **Terminal attempt status `closed`** (migration `0019_attempt_closed`, partial index `ix_attempts_open` on the polled set): the reconciler closes an attempt whose payable is expired/cancelled/refunded, older than 72 h, and whose fresh re-query says unpaid/not found. Routing of notifies is by `gateway_ref`, so a late payment on a closed attempt still settles (held as late). The Operations overview shows `open_payment_attempts` and `paid_undelivered_auto_card`.
- **Second trade on a refunded order** takes the duplicate-payment path (critical audit + staff refund alert); `UNIQUE(order_id)` on payments means no second Payment row.
- **Redirect gateways** count as OK only after a verified notify/settlement or a passing self-test.
- **Dead delivery jobs** (8 failures) raise a staff alert from the API reconciler (deduped per job); the delivery process stays without egress.
- **Periodic jobs** take a Redis lock per pass (compare-and-delete release, 10 min TTL). Reconciliation deliberately stays *before* order expiry: reversing it would expire an order paid just before its deadline whose notify was lost, and hold it as a late payment.

Consequences: no held order or attempt is stranded; every exit is audited and fails closed on missing evidence. Closing attempts reduces gateway query volume. A USDT attempt without a `trade_id` cannot be re-queried and therefore is never auto-closed (staff resolve it). Running the job loop in its own process was not done (one API replica in production); the lock makes a second replica safe.


### ADR-036: Email change needs proof of ownership (issue #72 S6)

Context: `POST /me/credentials` stored a new email immediately (marked unverified). Anyone signed in could squat an address on their account, blocking its real owner from registering, and the distinct conflict reply told them whether an address was registered.

Decision: `POST /me/email-change` (current password unless the account is instant) sends a one-time code (`auth/codes.py`, purpose `email_change`, bound to the user id and the new address; registration TTL, attempt and send limits plus per-user/per-IP request limits) and always answers `{"sent": true}`; a taken address gets no mail, and sending runs in the background so timing does not differ. `POST /me/email-change/confirm` verifies the code, re-checks uniqueness, sets the email as verified, clears `is_instant` and audits `me.email_changed`. `/me/credentials` is password-only. Unlike registration (which may accept unverified addresses when `email_verify_on_register` is off), an email change always needs a code: with no mailer configured it answers 403 `feature_disabled`.

Consequences: an unconfirmed address is never stored as a login email. Deployments without SMTP cannot change emails (instant accounts can still set a password). Sessions are not revoked on an email change (only on a password change), matching the existing convention.

### ADR-037: v11 — product variants, Telegram-style chat, notifications, announcements, manual service records

Context: the owner asked for variants with their own prices and service terms, a shorter home, admin pinning/sorting, CS alerts that work while the browser is minimised, buyer message alerts and typing status, real replies/pins/edits in chat, announcements with unread state, staff-entered service reminders for off-site sales, and generic avatars. Spec and per-workstream notes: [review-v11-features.md](review-v11-features.md).

Decision:

### ADR-038: Multi-supplier procurement in its own process (review-v12)

Context: the owner wants products fulfilled automatically from upstream suppliers (first: ZovoCard CDKs, virtual cards and direct top-ups), several sources per variant with failover, while manual handling stays the primary exit and no real funds move before the independent security review. Supplier calls need internet egress and supplier API secrets; the delivery process must keep its boundary (internal network, sole holder of vault private keys). Vendor behaviour is irregular: many errors carry no `error_code`, an HTTP 200 can carry `code != 0`, idempotency replays cache only 2xx, a card recharge "pending" is a 400 without a code, and webhooks are lossy. Spec: [review-v12-procurement.md](review-v12-procurement.md).

Decision:
- **New process `python -m app.procurement`** (compose profile `procurement`, own env file `deploy/env/procurement.env`, own egress network, DB role `app_procurement`, Redis user limited to `rl:proc:*`). It holds the supplier API secrets (from env, by supplier `code` and `env`: `<CODE>_APP_SECRET` / `<CODE>_SANDBOX_APP_SECRET`, never in the database) and only the vault **public** key. `app_procurement`: full on the five procurement tables; INSERT on `audit_log` (+ SELECT of its id); SELECT on needed columns of `tenants`, `orders`, `products`, `product_variants`; no UPDATE on orders, nothing on `deliveries`, nothing on `card_stock` / `outbox` until M2 first writes them (its migration adds INSERT then). `ProcurementSettings.env` defaults to `prod` when `APP_ENV` is missing (no mock adapter, https only). A SELECT-only policy lets the health loop find enabled suppliers across tenants; every write pins the tenant. Process hygiene is tested: no FastAPI/pydantic/`app.modules`/`app.core.config`.
- **Adapter layer `app/suppliers/`** (no imports from `app.modules`): `Supplier` protocol (`probe`, `balance`, `availability`, `submit`, `query`, `void`, `verify_webhook`) returning one of six `Outcome`s (`OK`, `ACCEPTED_PENDING`, `RETRYABLE`, `UNAVAILABLE`, `FATAL`, `AMBIGUOUS`); the engine understands only these. Failover only on `UNAVAILABLE` (as ADR-034).
- **ZovoCard client**: one table maps (HTTP status, `error_code`) to an outcome; `msg` is never read; an unrecognised 4xx/5xx on a write is `AMBIGUOUS` (reconcile by query, resubmit only with the same key), and so are HTTP 500 / `internal_error` / the catch-all `request_failed` on a write (reads: `RETRYABLE`); account-level refusals (401, 403 allowlist, insufficient balance, missing permission, `request_failed`) also open the supplier breaker. `channel_unavailable` / `product_unavailable` stay `UNAVAILABLE` (vendor: refused before any charge). `GPT_PRICE_UNCONFIRMED` / `GPT_PREFLIGHT_RATE_LIMITED` are `RETRYABLE`: re-preflight, then resubmit under the same key. Vendor error codes are reduced to `[A-Za-z0-9_.:-]{1,64}` before they reach logs, health or audit rows. Every write carries an `Idempotency-Key` in the vendor format (`pj:<job hex>:<step>`, committed before the HTTP call); a 60/min token bucket; 10 s connect / 40 s read timeouts; logs carry method, path, status, error code and a key hash, never bodies or secrets. **Any non-GET request to a production supplier is refused in-process unless `APP_PROCUREMENT_ALLOW_PRODUCTION_WRITES=1`**, which no env file sets. Amounts are `Decimal(str(x))`.
- **Availability** of a plan = `registry[key].purchasable is True and plans[registry[key].acc_plan_key].enabled is True`; a missing or non-boolean field means unavailable.
- **Admin "Suppliers"** (session admins, audited): configuration rows only, **platform tenant only** (orchestrator/owner decision 2026-11-14: the env-file credentials belong to the platform deployment; reseller tenants get no suppliers). `app_api` may UPDATE only the admin-editable columns. Codes are the adapter name or `<adapter>_<suffix>` and never end in `_sandbox` (API, registry and DB check), so a row can only select its own vendor's credential set. "Test connection" goes API → `procurement:8004/internal/probe` with its own token (`APP_PROCUREMENT_TOKEN`, distinct from the delivery token), mirroring the reveal call: the API never holds a supplier API secret. A production supplier cannot be enabled until `APP_PROCUREMENT_ALLOW_PRODUCTION` is set (owner rule, AGENTS.md §1.11); "Test connection" stays allowed for it, because the probe is GET-only and the owner wants to check the real key.
- **Schema** (migration `0023_procurement`, FORCE RLS): `suppliers` (unique per tenant, code, env), `supplier_offers`, `procurement_jobs` (unique idempotency key; one live job per order unit), `supplier_events` (unique per supplier + dedup key), `supplier_ledger` (unique per supplier + external id; `balance_change` only).

Failover on `UNAVAILABLE` will additionally need a `query()` by idempotency key that finds nothing, once M2 implements `query()`.

Consequences: supplier compromise or misbehaviour is contained in a process without private keys or delivery rights, and the API never sees supplier credentials. Polling remains mandatory because webhooks are hints. `procurement_egress` is general egress, not an allowlist: restricting it to the supplier hosts is an open item before go-live. M1 ships the adapter, schema, process and probe only; no order reaches a supplier until M2 adds the `upstream_*` delivery modes, the job engine, webhooks, ledger and breaker. Existing deployments migrate unchanged (the role is created NOLOGIN without `APP_DB_PROCUREMENT_PASSWORD`; set it and `ALTER ROLE app_procurement LOGIN PASSWORD ...` before enabling the profile).

### ADR-039: Optional two-factor login (TOTP) (review-v12 §13, issue #72 S8)

Context: staff and buyers log in with a password only (Google for buyers). #72 S8 asked for a second factor for staff; the owner wants it optional for everyone, never a condition for logging in. (ADR-038 is the v12 procurement record on `feat/v12-procurement`.)

Decision:
- RFC 6238 (SHA-1, 6 digits, 30 s, ±1 step) with the standard library only (`app/core/totp.py`); no new dependency.
- `user_totp` (migration `0022a_user_totp`, FORCE RLS, `app_api` only): secret sealed with AES-256-GCM under a key derived from the settings key and bound to tenant and user (the card vault is not involved); ten recovery codes stored as keyed hashes; `last_step` moves forward in one conditional UPDATE, so a code is accepted once.
- Login is two requests: a correct password for an enrolled account returns a pending token (Redis, 300 s, single use, five wrong codes) and **no session**; `POST /auth/login/2fa` turns token + code into the session. Wrong codes count against the password step's limiter keys plus a per-account counter. Google sign-in of an enrolled account is redirected to the same second step with the token in the URL fragment.
- Enrolment needs the password (except one-tap and Google-linked accounts), shows the secret once with a QR drawn by our own server, and ends the account's other sessions. Turning it off needs a code or a recovery code. An admin can reset the second factor of a buyer or an agent (audit severity critical, sessions and API tokens ended); nobody can reset their own without a code, and an admin's second factor cannot be reset from a session at all.
- A Google link or an emailed password reset that proves ownership of an unverified-email account also deletes a second factor enrolled by whoever registered the address first.
- Limits (security review 2026-11-16): a guess is counted against the per-account budget (10 per hour) before it is checked and given back on success, so parallel requests cannot overshoot it; at most 10 pending tokens per account per 10 minutes.

Consequences: a stolen password alone no longer opens an enrolled account. A lost phone is covered by recovery codes, then by an admin reset; an admin who loses both needs a database-level reset (`DELETE FROM user_totp WHERE user_id = …` as the owner role). Accepted residual risks: (1) one-tap and Google-linked accounts enrol without a password, so a stolen session of such an account can enrol the thief's device and lock the owner out until an admin reset; (2) a person who knows the password can use up the account's ten wrong codes per hour and so block its second step for that hour; (3) rotating `APP_SETTINGS_KEY` invalidates every sealed secret and recovery hash (no key id in the blob): rotation needs a reset of all enrolments; (4) the account's API tokens stay valid when 2FA is turned on (they are admin-issued and scope-limited). "Require 2FA for staff" is not built (it needs a forced-enrolment flow). The migration id sorts before the v12 chain: when v12 reaches `main`, `0023_procurement` must revise `0022a_user_totp`.

### ADR-048: Direct orders pick and fund their card themselves; sold out only when no money can pay (owner request 2026-11-19)

**Context:** production ChatGPT plans all showed sold out with USD 19–33 in the ZovoCard wallet. The Open API pays a

right before the order, then reads the card in real time and refuses an order the card cannot pay. (4) Stock = a card or
an allowed top-up can pay. (5) A PAID order that meets no card / no money / no price / the cap goes to staff at once
(`needs_manual`), never the 30-minute card wait. (6) Before a hand top-up staff run the charge check (payment, supplier
order, the job's top-ups, the funding card's latest spends) and must confirm it (`charge_checked`).
**Consequences:** money only ever moves wallet -> our own card (refundable); an unclear top-up stays counted against the
cap and stays on the job: only THAT top-up (same card, same key) may go again, and not at all once the card holds the money
(payment audit H1); only the vendor's documented refusals mark a top-up failed; a failed wallet / catalogue read is a retry,
never "no money"; the caps are per tenant; a direct hand fulfil needs a charge check run by the same staff member in the
last 30 minutes (server-side marker); issuing NEW cards per order stays reserved (§21.4) until the owner asks.

### ADR-049: Open new funding cards on demand, sweep used-up cards, alert on a low wallet (owner 2026-11-21)

**Context.** ZovoCard allows each card 3 Go/Plus ("light") uses. Once every card had used its 3, plans showed sold
out although the wallet held money ("Out of Stock" on 2026-11-21). Money also stayed stuck on used-up cards (card
·8575: USD 12.62). The owner approved: open cards on demand, keep the card's balance at what the order needs, move
leftovers back, pick card ranges by the BIN list, switches on by default, a Telegram alert below USD 60 ("simple and
efficient; security is not a priority for now").

**Decision.**
- `tenants.funding_settings` gains `auto_open_cards` and `sweep_leftover` (default **on**, but they act only
  while the master switch `auto_recharge` is on, which stays off by default for a new tenant and is on in production),
  and `wallet_alert_usd` (default 60, 0 = off). Saved through the same 2FA-gated console call.
- **Open on demand.** When `auto_existing` finds no card with a use left and the wallet covers the opening fee + the
  first load: the storefront check only reports the plan in stock (nothing is spent while buyers browse); the FRESH
  check of a paid job (`availability_fresh`, engine pre-check) calls `POST /cards/open` and offers the new card as the
  only candidate. Product: the owner's BIN priority, then the smallest total; never one whose `restricted_merchants`
  blocks the product's checkout. First load = the order's card need (price + vendor buffer + FX margin) in whole
  dollars, at least the product minimum. Cardholder name = the newest card's. Idempotency key = hash(card ids, product,
  UTC hour): concurrent checks and retries open one card. The engine records it in `procurement_fundings`
  (`kind='open'`, fee + load) against the daily cap and audits `procurement.card_opened`.
- **Sweep.** After a direct order's submit / query, cards whose uses for that tier are spent (usage `remaining == 0`,
  not busy / cooling / reserved, ACTIVE) move `balance - refund_keep_min` (vendor value; USD 1 when not stated) back
  to the wallet with `POST /cards/refund`, if at least USD 1. Never a card bought for a buyer (id and masked-number
  clash checks, as for candidates) and never a card with a job in flight. Recorded as `kind='sweep'` (never counted
  as spending), audited `procurement.card_swept`. Pro 20x uses on those cards stay; a later Pro order tops up again.
- **Wallet alert.** The API reconciler compares the ZovoCard production balance procurement last recorded (fresh
  within 2 h) with `wallet_alert_usd` and sends one Telegram alert per 6-hour window while it stays low.
- Vendor setting changed by hand on the owner's word (2026-11-21): `count_failures=false` for gpt / claude / grok
  card rules, so a blocked checkout (not charged) no longer spends one of a card's 3 uses.
- Migration `0039_card_open_sweep` widens the `kind` check to `recharge|open|sweep`.

**Consequences.** Plans stay in stock while the wallet can open a card (about USD 19.50 for Plus PH: fee 1.50 +
first load 18). Each card costs USD 1.50 per 3 orders. Money no longer piles up on used-up cards. A failed opening is a
retry of the pre-check (`card_open_failed`); a successful opening whose ledger write failed is still visible in the
vendor's card list. The wallet itself is still topped up by hand (USDT to the vendor's EVM deposit address); an
automatic refill from the OKX Agentic Wallet is a separate, later step.

### ADR-050: Every BEpusdt stablecoin network as a payment channel; receiving wallets managed from the admin (owner 2026-11-21)

**Context.** The owner wants Polygon PoS USDT next to X Layer and Alipay, and to "add other USDT addresses myself,
as versatile as possible". Channels were a fixed list of three in about ten places, and receiving addresses could
only be changed inside BEpusdt's own admin.

**Decision.** `payments/channels.py` builds the catalogue from what BEpusdt v1.24.3 supports: USDT on X Layer,
Polygon, Arbitrum, BEP20, Solana, TON, Aptos, Plasma, ERC20, TRC20 and USDC on X Layer, Polygon, Arbitrum, Base,
BEP20, Solana, Aptos, ERC20, TRC20 (channel id = trade type with `.` → `_`; cheap networks first; every crypto
channel off until switched on). Request schemas validate against the catalogue (`PayChannel`) instead of a fixed
`Literal`. The admin "Crypto wallets" panel (`/admin/payments/crypto`, platform admin session, no 2FA by owner
decision) lists, adds, switches, re-addresses and removes BEpusdt wallets through BEpusdt's admin API (entry page →
session cookie, login token in `Authorization`), checks each address against its network family (EVM, TRON, Solana,
TON, Aptos) and audits every change (`payments.crypto_wallet_*`). The frontend names any channel through the
shared `cryptoChannelLabel`.

**Consequences.** A new network is a switch and an address in the admin, no code. BEpusdt keeps the payment logic
unchanged (it converts the CNY amount; notifies are verified as before). The API needs the BEpusdt admin login
(`APP_BEPUSDT_ADMIN_USER/PASSWORD/ENTRY`). A switched-on network without an enabled wallet is flagged red in the
admin (BEpusdt would refuse the order).

**ADR-049 addendum (2026-11-21).** Paid direct orders not sent yet reserve their USD cost × 1.08 from the wallet in
the sold-out check (never two big orders against the same money); the leftover sweep also runs every 30 minutes;
offers are re-checked right after each direct job.

### ADR-051: Per-product markups, charm price endings, whole-yuan payment fees (owner 2026-11-21)

**Context.** One shop-wide 12 % markup on the official price was "too uniform". The owner set Pro 5x at about
7.90 %, Pro 20x 7.93 %, Pro 50x 6.04 % (Go and Plus unchanged), wants prices ending in 9 / 8 / 99 rather than round
hundreds, rounded in the seller's favour, and a whole-yuan amount both for the listed price and for what the buyer pays
after the Alipay surcharge.

**Decision.**
- Cost model: `markups` (same keys as `targets`: product or product:variant) override `target_markup` per unit;
  `PUT /admin/procurement/pricing/target` with a `markup` field sets / clears one (audited
  `pricing.markup_updated`). The pricing panel edits markups when the shop is in markup mode.
- `price_ending` (0 = off, 1–9): a recommended price rounds UP to the next whole price ending in that digit (9 in
  production), so it never drops below the markup and never lands on a round hundred.
- `payments.fee_round_whole` (Settings → Payments, audited with `site.updated`): every channel fee is rounded UP to a
  whole currency unit (`fee_minor(…, whole=True)`), server side in every fee path (order, pay-time re-apply,
  checkout, reprice) and mirrored in the buyer previews (`lineFee`), so a whole price gives a whole total
  (729 + 37 = 766). The DB invariant `amount = subtotal − discount + fee` is unchanged.
- Prices still change only through the audited "Apply" of the pricing panel (server recomputes the recommendation).

**Consequences.** Recommendations sit slightly above the target markup (up to 9 yuan for the ending, e.g. Pro 5x
US 7.9 % → 721 → 729, 9.1 %). Buyers pay up to 0.99 yuan more in fees per order with whole-yuan fees on.

### ADR-052: Upgrades of a running ChatGPT plan priced from the vendor quote; chat read state (owner 2026-11-22)

**Context.** A buyer holding Plus could not buy Pro 5x: the pre-payment check refused every account whose vendor
`can_purchase_at` lay in the future (`purchase_not_yet`), while ZovoCard's own direct top-up upgraded the same account
for the difference (`POST /gpt-direct/upgrade-quotes`). The same rule refused a FREE account that the vendor then served
at once, so the date is not a block on its own. Support staff also had to reply to clear the unread dot (the inbox never
called the existing staff read endpoint).

**Decision.**
- Upgrades: when the account holds Go / Plus / 5x and the target is a higher Pro plan, the account check asks the vendor
  for the upgrade quote; available = passed (with the quote), none = `upgrade_unavailable`. The order is priced on the
  server from it: `USD difference × shop rate × (1 + the unit's markup)`, rounded like recommendations (whole units,
  price ending), never above the list price; the credit is stored in `orders.terms.upgrade` and shown as "Upgrade credit
  −¥X" before payment (buyer order page, admin drawer). Execution orders with the upgrade's own token and currency; an
  order paid at the upgrade price whose account is no longer upgradable stops (`upgrade_unavailable`, staff) and never
  buys the full plan; the upgrade cost is bounded by what the buyer paid for (`JobSpec.upgrade_max_usd`, migration
  `0040` lets procurement read `orders.terms`).
- `purchase_not_yet` now applies only to an account that holds a plan (`has_active` or a paid `currentPlan`).
- Refusals tell the buyer which account was checked, its plan and from when it can buy again (and that nothing is
  wrong / nothing was charged); procurement logs the plan state of every pre-check.
- Chat: the inbox calls `POST /admin/conversations/{id}/read` when a chat is opened / a message arrives while it is open;
  conversation rows carry `awaiting_reply` (buyer wrote last) and `peer_read_id`; a realtime `read` event clears the
  dot for every agent and updates the read receipts ("Read" / "Sent" for the buyer, "Read by the buyer" for staff).

### ADR-053: Upgrades sell at the list price; optional renewal cancel; sessions judged by the session token (owner 2026-11-25)

**Context.** The owner does not want to lose money on upgrades whose remaining coverage is large: a buyer paying only the
difference (ADR-052) can cost more than they paid. Production 2026-11-24 also showed ZovoCard refusing accounts with
`checkout_unusual_activity` (OpenAI risk control) and once with a `:401` after which the session may be unusable, and the
shop refused sessions whose short-lived access token had expired although ZovoCard renews it from the session token
(docs 6.18b). ZovoCard offers `POST /gpt-direct/cancel-renewal` (session only, 6.19).

**Decision.**
- Funding settings (2FA write, audited) gain two switches, both OFF by default: `upgrade_pay_difference` (on = the ADR-052
  difference pricing) and `cancel_renewal_before_upgrade` (on = call cancel-renewal right before each upgrade order;
  logged, never blocks). By default an upgrade order costs the full list price (credit 0, nothing shown); procurement
  still uses the vendor's upgrade quote as the cheaper way to deliver and may buy the full plan when no upgrade is
  offered (`upgrade_max_usd` is only set for difference-priced orders).
- A pasted session is refused only when its own `expires` has passed (server and client); an expired access token is
  accepted.
- The latest failed vendor event of a direct job gives the buyer a reason: `account_flagged` (risk control) or `session`
  (refused / expired / 401), with instructions for a fresh session (computer, new Chrome Incognito window, e-mail and
  password sign-in, no passkey, no phone) and that support was told. Vendor `GPT_SESSION_INCOMPLETE` warnings are logged.

**Consequences.** Upgrades earn the full margin by default; staff can switch to difference pricing and renewal cancelling
without a deploy. Buyers stop resubmitting dead sessions blindly.
### ADR-054: card.zzshu.pro as the standby provider of ChatGPT direct top-ups (owner 2026-11-25)

**Context.** ChatGPT direct orders depend on ZovoCard alone. Its checkout sometimes fails BEFORE any charge
(`failed_precharge`, vendor event codes such as `checkout_unusual_activity`, `checkout_pricing_unavailable:401`); those
jobs stopped in `needs_manual` although nothing was spent. card.zzshu.pro offers the same top-up through
`POST /orders/direct` (vendor docs: `docs/research/zzshu/zzshu-gpt-api.md`) but is paid with a bank card WE hand over
per order together with the buyer's session, and it has no idempotency key.

**Decision.**
- Adapter `zzshu` (`app/suppliers/zzshu/`, own bounded client: 5 s / 30 s timeouts, 1 MiB cap, strict parsing, production
  write guard). Plans: go -> `go`, plus -> `plus`, pro_5x -> `pro5`, pro_20x -> `pro20`, always the FULL-price types
  (upgrades are sold at full price, owner rule); regions PH, US, EG, CL (no JP). plus_half, pro_50x, Claude and Grok have
  no zzshu source (the admin refuses such a source). Secret `ZZSHU_APP_SECRET` (API key), optional `ZZSHU_BASE_URL`,
  `ZZSHU_FUNDING_SUPPLIER` (default `zovocard`, the supplier whose wallet funds the cards). Migration `0041` lets
  `suppliers.adapter` be `zzshu`.
- Points gate: `GET /user` points < 1 (or unreadable) = the source is not used (`points_exhausted`), fail closed, cached
  60 s.
- Dedicated card (mitigates sending a PAN to a third party): every order gets a NEW ZovoCard card opened just for it
  (ADR-049 code: the owner's BIN priority picks the product) and loaded with `offer cost (USD) x (1 + margin)`, whole
  dollars up; margin = funding setting `zzshu_card_margin_pct` (default 20, 0-100, admin Funding panel). It needs the
  `auto_recharge` master switch and the daily cap, like every automatic wallet spend. Number / expiry / CVV are read from
  `GET /cards/{id}` right before the one POST and the buyer's session comes from the sealed credential; both live in
  memory for that call and are never stored, logged, audited or put in an exception. When the order is over (success or
  failure) the leftover goes back (`POST /cards/refund`, then `DELETE /cards/{id}`) and the card id, last four, loaded
  amount and leftover are recorded on the job (`card_id`, `card_last4`), in audit rows `procurement.zzshu_card` and in
  the job timeline. A card that could not be swept raises `procurement.zzshu_card_unswept` (staff alert). The card is
  never offered as a ZovoCard funding card (in-process exclusion set + `funding_card_clash`-style job record).
- No idempotency key: the create is sent at most once per job. A create whose answer is lost is AMBIGUOUS, the job goes
  to `needs_manual` (`create_unconfirmed`) with the card left untouched (it may be charged); staff check the zzshu
  history. 429 / 42902 and 502 / 50300 mean nothing was created: retried with the SAME card. A definite refusal (40020,
  40305, 40306) sweeps the card and goes to staff. A zzshu `failed` (re-read after 2.5 s as the docs advise) ends in
  `needs_manual` with the card swept, never in a third source.
- Fallback (the one exception to "a job holding a supplier order is never moved"): a ZovoCard direct order that failed
  DEFINITELY before any charge, i.e. status `failed_precharge` with its service fee and funding hold released / refunded /
  none (`Result.precharge_clean`, set by the adapter), fails over to the zzshu source of the same variant. Declined,
  cancelled, a held or settled fee, a missing fee status or an unread order stay in `needs_manual`. The ZovoCard order id
  stays in audit `procurement.precharge_failover` and in the job timeline; the job forgets the ZovoCard card / account
  mask and starts the zzshu source like a fresh job (new idempotency key).
- Primary switch: by hand with the existing source tools: give the zzshu source a smaller `priority` than the ZovoCard
  one (or disable the ZovoCard offer); both are normal sources of the variant. Automatic: every definite pre-charge
  failure of a ZovoCard direct order counts in Redis (`rl:proc:pcf:<supplier>`, fixed 60-minute window); at 3 the
  supplier's direct sources are put BEHIND the others for 30 minutes (`rl:proc:cool:<supplier>`; constants in
  `procurement/engine.py`), one critical audit row `procurement.direct_cooldown` is written and the API reconciler sends
  the Telegram alert. Demoted, not removed: with nothing else usable ZovoCard is still tried. The breaker columns were
  not reused: a supplier breaker stops the supplier's CDK and card products too.

**Consequences.** A pre-charge ZovoCard failure no longer needs staff when a zzshu source exists. A card number does
reach a third party (zzshu), which is why each card is new, holds only the plan cost plus the margin and is deleted at
the end; a zzshu order that charged more than expected is limited by the margin. Each zzshu order costs a card opening
fee; the wallet and daily cap guard it. The procurement Redis ACL only allows incr / expire / get / ttl, so the window is
fixed, not sliding. Open: the real vendor's `funding_hold_status` values are unknown (a value outside released /
refunded / none blocks the fallback, safe); zzshu's `is_subscription_cancelled = 0` after success is delivered anyway and
recorded as `completed:renew_unconfirmed` for staff; a card left over after a lost create must be reviewed by hand.

### ADR-055: vmcardio as the second issuer of the zzshu dedicated card (owner 2026-11-25)

**Context.** Every card.zzshu.pro order is paid with a NEW dedicated card (ADR-054), opened at ZovoCard. When ZovoCard
cannot open one (wallet too low, no product / slot, vendor refusal) the order stops although zzshu itself is ready.
vmcardio.com (research: `docs/research/vmcardio/vmcardio-api.md`) issues cards through a V2 API and returns the number /
CVV / expiry the zzshu create needs. It is used for nothing else.

**Decision.**
- Adapter `vmcardio` (`app/suppliers/vmcardio/`): V2 only, base `https://vmapi.vmcardio.com` (sandbox
  `https://sandbox-api.vmcardio.com`). Own bounded client (5 s / 30 s, 1 MiB cap, no redirects, production write guard
  on `createCard`). `GET /v2/getAccessToken` -> token cached in memory and refreshed 600 s before `expired_time`;
  an "invalid token" answer (400003, never processed by the vendor) refreshes once and repeats. The supplier row is
  `vmcardio` (env production / sandbox); it has no capabilities: no offer can be created on it and it never takes
  CDK / VCC / direct jobs. Secrets only in the procurement env: `VMCARDIO_APP_ID`, `VMCARDIO_APP_SECRET`, optional
  `VMCARDIO_BASE_URL` (`..._SANDBOX_...` for the sandbox) and the cardholder data `VMCARDIO_CARDHOLDER_FIRST_NAME`,
  `_LAST_NAME`, `VMCARDIO_CARD_ADDRESS_LINE1`, `_CITY`, `_STATE`, `_POSTCODE`, `_COUNTRY` (default US); the address
  is sent only when complete, the name defaults to a neutral one. Probe = token + balance + products; the balance
  refresh feeds the same wallet-low Telegram alert as ZovoCard. Migration `0042` allows the adapter and widens
  `procurement_jobs.card_id` / `procurement_fundings.card_id` to 64 (a vmcardio id is about 22 characters).
- Issuer order: `ZZSHU_FUNDING_SUPPLIER` is now an ordered, comma separated list of supplier codes (default
  `zovocard`; `zovocard,vmcardio` in production). The funding setting `zzshu_card_issuers` (default
  `["zovocard","vmcardio"]`, 1 to 4 distinct codes, each must be a ZovoCard / vmcardio supplier row, admin Funding
  panel, 2FA + audit like the other funding settings) orders them at run time; a code not configured in the
  procurement env is skipped. `CardIssuers` (`app/suppliers/issuers.py`) replaces the single ZovoCard supplier a
  `ZzshuSupplier` held and routes `open / read / finish` by issuer; a card id `vm:<vm_card_id>` is vmcardio, a number is
  ZovoCard. The next issuer opens a card only after a DEFINITE "nothing opened": UNAVAILABLE (wallet low, no product /
  slot, cap, `product_unavailable`), or a coded refusal before any card exists. RETRYABLE / AMBIGUOUS is raised as is.
  Settings `vmcardio_bin_priority` (default 537872, 537882, 532604, 555659; only these BINs are ever used, the product
  is looked up through `/v2/getProductCode`, never hard-coded) and `vmcardio_reserve_slots` (default 1: a product whose
  `remaining_open_card_num` is at or below it is skipped, so slots stay for other uses).
- Same lifecycle and safeguards as the ZovoCard dedicated card: the card is loaded with `need` (cost x (1 + margin), whole
  dollars up, at least 1) from the vmcardio account balance, only if the per-top-up max and the daily cap allow it, and
  `topups.record_open` counts it against the daily cap; its id is persisted on the job BEFORE the zzshu send (the
  `card_opened` re-lease); at the end `refundCard` (balance above the vendor's 0.10 USD minimum) then `deleteCard`
  (returns the rest) sweep it; a card that could not be deleted raises `procurement.zzshu_card_unswept`; the staff
  timeline and the audit rows show issuer, card id, last four, loaded and leftover. Number / CVV / expiry come from
  `/v2/cardDetail` right before the one zzshu POST and live in memory only; `getCardList` also returns full numbers, so
  its reply is reduced to id / amount / time at once. Nothing is logged, stored, audited or put in an exception.
- Idempotency and lost answers: request id `zz-<job uuid hex>-open` (unique per app forever; the vendor answers
  `Duplicate Client Request Id` and not the first result) and card `label` = `zz-<job uuid hex>`. A timeout or 5xx after
  the send is RETRYABLE: the engine retries with the SAME key, the repeat answers "duplicate" and the card is looked up
  in `/v2/getCardList`. The vendor's list and detail do NOT return the label, so the lookup takes the ONE active card
  created in the last 45 minutes that holds exactly the loaded amount (the list gives no time zone: a time that is recent
  as UTC or as UTC+8 counts). None yet = retry (the list may lag), several = AMBIGUOUS for staff; a second card is never
  created under a new id. The label is visible in the vendor console for the staff check.
- Webhook `POST /api/v1/webhooks/vmcardio` (API process, CSRF exempt, 300 / min / IP like the ZovoCard one, 64 KiB):
  `X-VM-SIGN` (Base64 RSA-SHA256 PKCS#1 v1.5 over the RAW body) is verified when `APP_VMCARDIO_WEBHOOK_PUBLIC_KEY` (PEM)
  is configured (bad signature 401; an unreadable key 503, never a silent downgrade). Without a key the event is
  accepted and stored with `verified: false`. In both cases it is only a hint: a whitelisted payload (ids, status, type,
  amounts, merchant / description with every run of 4+ digits masked, no card number) goes to `supplier_events`
  (kind `vmcardio_card_transaction`, already marked processed, NO outbox row) for staff and ops review; money, jobs and
  orders are never touched. The reply is `{"code":0,"msg":"ok"}`.

**Consequences.** An order no longer stops when ZovoCard cannot open a card, while ZovoCard stays first and vmcardio is
used only on a definite refusal. Open: the vendor's real card-detail `expire` format is unknown (the parser accepts
`MM/YY`, `MM/YYYY`, `YYYY-MM`, `MMYY`); the opening fee of a vmcardio product is not in the API, so only the loaded amount
counts against the cap; a ZovoCard "request_failed" on open is AMBIGUOUS (not a definite refusal) and so never falls back;
the memory of "which issuer answered with a maybe-opened card" is per process (a restart asks the first issuer again);
the webhook key is still to be found in the vendor console.
